# Database Migration Skill

Use this skill when you need to generate and apply the initial database schema for a project before the Software Engineer begins coding.

## When to Use

- Architecture document contains a database schema section (Supabase / PostgreSQL)
- A new project needs its schema applied to Supabase before code is written
- An existing project needs schema changes applied as a migration

## Core Principle

**Write first, then run.**

Always commit the migration file to GitHub before executing it in Supabase. This creates an auditable record of every schema change.

---

## Process

### Step 1 — Extract the Schema

Read the architecture document provided in your prompt. Find the database/schema section. Identify:
- All tables (name, columns, data types, constraints)
- Foreign key relationships and CASCADE rules
- Indexes for frequently queried columns
- Row Level Security (RLS) policies
- Any triggers or functions (e.g. `updated_at` auto-update)

### Step 2 — Write the Migration File

Generate a single `.sql` file following this structure:

```sql
-- Migration: initial_schema
-- Project: {project_name}
-- Generated by: Database Engineer Agent

BEGIN;

-- ── TABLES ──────────────────────────────────────────────────────────────────

CREATE TABLE IF NOT EXISTS table_name (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  -- ... columns ...
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

-- ── INDEXES ─────────────────────────────────────────────────────────────────

CREATE INDEX IF NOT EXISTS idx_table_column ON table_name(column);

-- ── UPDATED_AT TRIGGER ───────────────────────────────────────────────────────

CREATE OR REPLACE FUNCTION handle_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER set_updated_at
  BEFORE UPDATE ON table_name
  FOR EACH ROW EXECUTE PROCEDURE handle_updated_at();

-- ── ROW LEVEL SECURITY ───────────────────────────────────────────────────────

ALTER TABLE table_name ENABLE ROW LEVEL SECURITY;

CREATE POLICY IF NOT EXISTS "Users can read own data" ON table_name
  FOR SELECT USING (auth.uid() = user_id);

COMMIT;
```

**Rules:**
- Use `IF NOT EXISTS` for every `CREATE TABLE`, `CREATE INDEX`, `CREATE POLICY` — makes the migration idempotent
- Use `UUID PRIMARY KEY DEFAULT gen_random_uuid()` for all primary keys
- Always include `created_at` and `updated_at` timestamps
- Enable RLS on every table that contains user data
- Wrap the entire migration in `BEGIN; ... COMMIT;`

### Step 3 — Commit to GitHub

Write the file to the repository using `create_or_update_file`:

```
Path:    supabase/migrations/20260220000000_initial_schema.sql
Branch:  main
Message: "chore: add initial database migration"
```

Confirm the file was written before proceeding to Step 4.

### Step 4 — Apply in Supabase

Execute the migration in the connected Supabase project using the MCP tools:
- Preferred: `apply_migration` with the SQL content
- Fallback: `execute_sql` if `apply_migration` is unavailable

After execution, verify by listing tables to confirm all expected tables exist.

### Step 5 — Return Confirmation

Return a summary:
```
## Migration Complete

✅ File committed: supabase/migrations/20260220000000_initial_schema.sql
✅ Applied to Supabase project

Tables created:
- users
- projects
- ...

RLS enabled on all tables.
```

---

## DO NOT

- Call `read_document`, `get_document`, or any Google Docs tool — architecture is provided inline
- Create multiple migration files — one file per run
- Use `DROP TABLE` or `DELETE` unless explicitly instructed
- Skip the `IF NOT EXISTS` guards
- Leave RLS disabled on user-data tables

---

## Error Handling

If Supabase MCP tools are unavailable:
1. Still commit the SQL file to GitHub
2. Log: "WARNING: Could not apply migration to Supabase — credentials may be missing. Migration file committed to GitHub for manual execution."
3. Return success so the workflow continues

If the SQL contains errors (e.g. type mismatch, constraint violations):
1. Log the exact SQL error
2. Attempt to fix the offending statement
3. Re-apply if possible; otherwise log and continue

---

## Anti-Patterns to Avoid

- ❌ `INTEGER` primary keys — use UUID
- ❌ Missing `IF NOT EXISTS` — breaks idempotency
- ❌ No RLS policies on user tables — security risk
- ❌ Missing indexes on foreign keys — performance issue
- ❌ Storing secrets or hardcoded values in SQL
- ❌ Running destructive statements (`DROP`, `TRUNCATE`) without explicit instruction
